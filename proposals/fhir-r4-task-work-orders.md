# Complete FHIR R4 Task work orders for DIS

**Status** — Proposed Phase 1 binding for committee review. This proposal identifies the profile changes to make if the committee adopts the design.

## Decision proposed

Use FHIR R4 operations to submit a complete job or execution order between independently implemented actors. Define one required input named `workItem` of type `Task` for each submission operation. POST the profiled R4 `Task` directly as the request body in both synchronous and asynchronous modes. FHIR R4 permits a resource as the body when the invocation supplies exactly one resource input. The submitted Task contains every instruction or an authorized reference to it. Each field has one authoritative location. Successful result responses use R4 `Parameters`. [FHIR R4 Operations](https://hl7.org/fhir/R4/operations.html#request) · [FHIR R4 Parameters](https://hl7.org/fhir/R4/parameters.html)

| Exchange | Complete work order |
| --- | --- |
| **ITI-x1** · `POST [base]/$submit-dis-job` · Requester → Manager or externally invoked Integrated actor | A Job Task with one data request authorization and one or more payload sets. Each set carries the exact approved policy identity and any permitted supplied lookup reference. The Requester can convey the order as one identifiable artifact. The receiving actor independently validates authorization, policy and payload before acceptance. |
| **ITI-x3** · `POST [base]/$submit-dis-task` · Manager → De-Identifier | A separate Execution Task for one assigned ruleSet and payload set. It contains the compiled execution plan reference, ruleSet ID, stage ID when applicable, reversibility mode and any authorized task-scoped lookup reference. The De-Identifier receives the assigned data and instructions for its stage. |

The Manager is authoritative for job state. The De-Identifier is authoritative for execution of its assignment. An externally invoked Integrated actor receives the Job Task and manages its execution internally. Both profiles use R4 even when the selected payload uses another supported FHIR release. ## Candidate content binding

- **Identity and intent.** Require a scoped business identifier in `Task.identifier`, a coded job or execution type, `intent = order`, and `status = requested` on submission. Define the authority for actor identity, the scope of identifiers, and how equivalent retries differ from a new order. Separate business identifiers, resource IDs, polling URLs and audit correlation identifiers. Decide where responses or evidence need to carry the business identifier for correlation. The Manager correlates assigned work to the job. Use `Task.partOf` when disclosure of the parent reference is authorized.
- **Job authorization.** Define one coded authorization input with a reference or an attachment. Apply the existing authorization checks to the caller and every requested set. Require validation of the exact approved policy content, including the current signed-carrier and Manager-resolved modes.
- **Payload sets.** Use one coded `Task.input` per set. Carry the manifest as `valueAttachment` and group `setId`, `payloadBinding`, `payloadVersion` and `manifestFormat` in one required complex extension on that input. For the Job Task, include the exact approved policy canonical URL and version in the same group. Define how that group carries optional signed policy content and a permitted lookup reference. For signed content, prefer a local reference to a contained R4 `Binary` with `contentType = application/jose` and preserve the exact JWS bytes. Constrain the Job Task to unique set IDs and the Execution Task to exactly one assigned set.
- **Execution instructions.** Add coded inputs for the DIS Execution Plan Library reference, ruleSet ID, stage ID when applicable, and reversibility mode. Keep a protected lookup reference scoped to the assignment. Validate agreement between the assigned set, the plan and the ruleSet before execution. The plan retains the exact source policy identity and evidence URI.

## Results, status and cancellation

- **Synchronous exchange.** The caller submits a complete Task with `status = requested`. The receiver validates the work order, executes it and returns `200 OK` with the result package and evidence in `Parameters` in the same HTTP exchange. Retaining or exposing a completed Task is optional.
- **Asynchronous exchange.** The caller submits the same complete Task. Once the receiver accepts the work, it returns `202 Accepted` with a `Content-Location` polling URL associated with the submitted `Task.identifier`. The caller retrieves the deferred `Parameters` outputs through ITI-x4 or ITI-x7. Document the DIS polling behavior and completion body. Keep job and execution modes independent.
- **Evidence and release.** A completed execution Task records the outcome of the assigned work. The Manager validates all required results and rechecks release authorization. Keep the DIS Result Package, mandatory DIS Evidence `Provenance`, and staged release `Provenance` for qualifying sets. The Manager controls what each recipient can see, including plan references, lookup material and intermediate results.
- **Shared status.** If DIS adopts independently readable status, define an authorized, limited view maintained by the receiving actor. Specify discoverability, permitted fields and retention separately from the full work order and result. A readable job state must distinguish terminal processing outcomes from retrieval errors. A completed Task exposed to a result-authorized caller may link to the same DIS Result Package using a coded `Task.output` with `valueAttachment.url`. Associate each output link with its `setId` and apply the existing release checks.
- **Cancellation.** If DIS supports cancelling accepted jobs, define an explicit authorized Requester–Manager interaction. Distinguish acknowledgement from terminal cancellation and define the outcome when cancellation races with completion. Once cancellation is accepted, the Manager blocks result release, stops dispatching and propagates cancellation to every active assignment. The Manager confirms job cancellation after reconciling all dispatched work. Work that already reached a terminal state keeps its recorded outcome. An in-flight synchronous ITI-x3 assignment needs an independent cancellation interaction keyed by an identifier known before completion. The capability declaration must make clear which combinations support cancellation.

## Profile update plan

| Step | Changes and exit criteria |
| --- | --- |
| **1. Agree the actor contract** | Update Volume 1 with the Job Task and Execution Task roles, authoritative state and assigned scope. Confirm identifier and retry semantics, and whether shared status and cancellation are part of the first revision or separately declared capabilities. Record the committee decision before changing conformance requirements. |
| **2. Draft both submission transactions** | Update ITI-x1 and ITI-x3 in Volume 2 with the direct Task body, admission checks, expected actor behavior and error responses. Cross-check ITI-x4 and ITI-x7 for deferred outputs, authorization and retention. Keep the success condition tied to validated results and the existing release rules. |
| **3. Define the FHIR artifacts** | Add Job Task and Execution Task profiles, input codes and the payload-set extension. Update both system-level OperationDefinitions and actor CapabilityStatements. Declare one required `workItem` input of type `Task` for each operation and specify the applicable Task profile for its direct request body. Mark submissions as state-affecting. Document the content mappings and protection rules in Volume 3. |
| **4. Demonstrate and verify** | Update the single-Patient synchronous example, a mixed R4/R5 multi-set submission, and a staged asynchronous example to show direct Task requests and Parameters results. Include both policy delivery modes and protected lookup where applicable. Add Test Plan cases for malformed Task inputs, missing or duplicate set metadata, mismatched payload versions, authorization or policy failure before acceptance, retry correlation, and result and Provenance parity. If cancellation is adopted, also test propagation, completion races, an in-flight synchronous assignment and withholding all output. Compile FSH, validate the examples against their declared profiles, and build the IG. |
