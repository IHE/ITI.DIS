# ITI.DIS Phase 1 full review

**7 November 2026 · Disposition: continue technical review before publication**

The working draft provides a coherent Phase 1 scope and enough material to review the principal workflows. The first blockers to resolve are the result encodings, composition of outputs from multiple ruleSets, and authorization at task retrieval and result release. These affect independent implementation even though the guide builds.

## Baseline and decision authority

Reviewed a copy of the working draft, including the local edits and new policy examples page, against commit `53efe270b78c3d9ec351a4d5085d06599d188d6b`. Volume 1 and the drafting plan govern the Phase 1 review. The plan records D01–D11 as agreed drafting decisions. The November review issues describe committee questions and discussion scope. They do not establish committee disposition of those decisions. The findings below cover the whole guide, including common security sections and evidence details beyond the scheduled Volume 1 discussions. Phase 1 uses R4 workflow resources, independently declared FHIR processing releases, the four actors and transactions in Volume 1, and an ordered plan per ruleSet. Bulk file delivery covers input and output for asynchronous cohort jobs. DICOM and CDA are proposed bindings. Data Recipient and push delivery remain open. ## Prioritized findings

**P1** blocks an interoperable or privacy-relevant conformance claim. **P2** materially weakens testability or publication quality. **P3** is editorial cleanup. Owners are proposed roles. All findings are open.

| ID | Priority and proposed owner | Finding and closure criterion |
|---|---|---|
| DIS-R01 | P1 · Transaction and FHIR editors | **Request and result wire definitions diverge.** ITI-x1 permits `processingTarget.resource`, `valueReference`, `valueUri`, and `valueAttachment`, while its OperationDefinition declares only `Resource`. ITI-x3 permits a bulk URI but declares only `Reference`. Volume 3 allows inline cross-release and by-reference results. Volume 2 and the OperationDefinitions describe ungrouped `output` as a resource. ITI-x4/x7 also lack a clear top-level `validationStatus` rule equivalent to the synchronous response tables. Publish a single field/type/cardinality matrix per exchange, including grouped/ungrouped exclusivity, exact ungrouped bulk and cross-release result forms, and protected task-only fields. Align the computable constraints and validate representative full messages against the operation contract. [ITI-x1 request](input/pagecontent/volume-2.md#23x1412-message-semantics) · [ITI-x3](input/pagecontent/volume-2.md#23x3-submit-de-identification-task-iti-x3) · [Operations.fsh](input/fsh/Operations.fsh) |
| DIS-R02 | P1 · Profile and policy editors | **RuleSet dispatch order leaves output composition undefined.** A payload set can have concurrent tasks and sequential stages, with one final result per set. The draft does not specify how outputs from concurrent tasks on the same resource are reconciled, or which stage result is handed forward. In the preliminary pseudonymization use case, the next stage could receive either the intended pseudonymized resource or the original. Define observable stage inputs, output authority and permitted overlap or rejection. Test two ruleSets editing the same resource and a later stage receiving the predecessor's validated output. [Policy rules and stages](input/pagecontent/volume-3.md#3pxx13-policy-rules-json-structure) · [Plan assembly](input/pagecontent/volume-3.md#3pxx15-policy-compilation) · [Stage isolation](input/pagecontent/volume-1.md#1pxx55-trust-isolation-between-stages) |
| DIS-R03 | P1 · Security and transaction editors | **Task polling lacks an explicit task-to-caller authorization rule.** ITI-x4 limits job retrieval to the original Requester or an authorized delegate. ITI-x7 requires credentials but does not give the De-Identifier a comparably explicit duty to authorize this Manager for this task before disclosing status, output, or the generated lookup table. Volume 1 also permits an IUA Authorization Client grouping where a responder needs Resource Server duties. Define roles for each interface, including source/result reads, and apply authorization at retrieval and release. Reconcile the Requester ATNA grouping table with the prose, and state the DIS transport option explicitly. ATNA grouping alone permits several transport options and does not guarantee mutual TLS. Test cross-Manager polling with a valid token and a known task URL, unauthorized use of intermediate result URLs, and the behavior when job authorization expires or is withdrawn before delivery. | DIS-R04 | P1 · Profile and FHIR editors | **Capability matching lacks a published declaration contract.** Volume 2 requires actor CapabilityStatements and matching on releases, bindings, actions, and transformation inputs. The FSH file is a TODO, and the guide lacks a machine-readable convention for several compatibility dimensions, including manifest formats. Publish per-role expectations, conditional option obligations, and a way to express compatible combinations. Demonstrate compatibility and rejection of a release/action/format combination even when its components are advertised separately. [ITI-x3 capabilities](input/pagecontent/volume-2.md#23x35-capabilitystatement-resource) · [CapabilityStatement source](input/fsh/capability.fsh) · [IHE Appendix Z.3](https://profiles.ihe.net/ITI/TF/Volume2/ch-Z.html#z.3-capabilitystatement-resource) |
| DIS-R05 | P1 · Payload and policy editors | **Two baseline action rules conflict with valid or predictable output.** `redact` requires an empty XHTML div, which fails the R4 Narrative non-whitespace requirement. The first-match example keeps one Identifier and removes the enclosing repeating identifier selection. The draft does not specify parent/child overlap or whether selection occurs on input or progressively modified data. Choose a valid redaction representation, replace illustrative bracket syntax with executable FHIRPath, and define conflict behavior or reject overlaps. Specify remaining action boundaries such as rounding ties, date-shift behavior at partial precision, and required fixed `Identifier` replacement fields. Reconcile the validation rule that forbids remaining direct identifiers in governed elements with the example that deliberately keeps one. Add positive and negative vectors. | DIS-R06 | P1 · Security and evidence editors | **Evidence and audit need distinct disclosure rules.** ITI-x1 requires processing target identifiers in the audit record and requires an evidence correlation identifier even for an accepted or rejected request that has no completed-task evidence. The transformation summary prohibits source values but permits a selector string that can contain an identifier literal. Define the correlation lifecycle for admission, execution, and multiple result sets. Reconcile all-poll audit language in Volume 1 with sampled in-progress polls in Volume 2. Specify safe recipient-facing summaries, and keep signed URLs and source identifiers out of recipient-visible evidence and diagnostics. That makes it unclear how a caller on a dual-mode interface selects synchronous submission. ITI-x7 groups all 4xx/5xx errors and tells the Manager to report task failure, even though a credential or transient server error can leave the task running. Test expiry and authorization separately from missing files, and test withholding at the actual result service as well as in the polling response. ## Committee decision brief

| Decision requested | Proposed disposition and consequence |
|---|---|
| Data Recipient and push delivery | Keep the existing standalone content-conformance path for Phase 1 unless the committee identifies an exchange that requires a distinct receiver. If adopted, define actor roles, authorization, delivery failure, evidence, and applicability before adding transaction obligations. Record the impact on UC-5 and potential MHD grouping. [Open issue](input/pagecontent/issues.md#data-recipient-and-push-delivery) |
| Multiple ruleSets affecting the same output | Specify how a stage consumes the prior stage's output. For concurrent work, require a defined observable result or reject a combination whose outcome is ambiguous. Assign the Profile and Policy editors to propose precise rules and assess effects on D01. R02/R05. |
| Phase 1 binding and version claims | Confirm mandatory FHIR support and which versions are independently declarable. Pin the R6 ballot edition before any provisional claim. Keep DICOM/CDA feasibility separate until the committee adopts a complete binding. R04/R11. |
| Authorization and evidence boundary | Confirm which IUA roles apply per interface, whether ongoing authorization is required at result release, and which correlation data each audience receives. Specify both testable access behavior and protected audit detail. R03/R06/R09. |
| Bulk result shape and polling | Approve one wire contract per supported delivery form, including terminal failure versus poll error and evidence correlation. Then align the artifacts and procedures under the existing D02/D11 scope. R01/R07/R08. |

Editorial corrections can proceed against the recorded baseline. Resolve the semantics above before freezing the affected artifacts. Policy discovery and lifecycle management remain future-phase design work under the issues page.
